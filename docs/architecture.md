# Byte Bot architecture and contracts

This document guides the five implementation phases. [The PRD](reference/byte_bot_prd.md) describes product requirements, and the [acceptance matrix](acceptance.md) defines expected behavior.

## Services and screens

React and TypeScript serve the transaction history at `/`, transaction details at `/transactions/:id`, the guided intake and evidence review at `/investigations/:id`, results at `/investigations/:id/results`, the report at `/investigations/:id/report`, and My Incidents at `/incidents`. Use relative API paths through the Vite proxy. Reloading a case or using browser navigation restores its persisted state. Screenshot preview is browser-local while the upload is open.

FastAPI handles the API and one bounded analysis workflow per investigation. Use PostgreSQL for durable data and a local CPU EasyOCR reader for screenshots. Run Gemini server-side for extraction. Keep settings, route handlers, storage, prompts, risk rules, and fixtures in separate modules.

## REST interface

Paths below are relative to `/api/v1`. Derive the current user from a server-issued, opaque demo cookie with `HttpOnly` and `SameSite=Lax`. Create the session on the initial transaction request and seed that session once. Scope all reads and writes by owner. Unknown and foreign resource IDs return the same `404` response. Reject malformed inputs and return useful errors for stale or conflicting operations.

| Phase | Endpoint | Contract |
| --- | --- | --- |
| 01 | `GET /health` | Return API readiness, including database availability. |
| 01 | `GET /transactions`, `GET /transactions/{id}` | List the session's seeded transactions and return a selected transaction's facts and actual status. |
| 02 | `POST /investigations`, `GET /investigations/{id}` | Create or reopen the session's case by transaction ID. Return the case, authoritative transaction facts, saved context, evidence, and any analysis state. |
| 02 | `PATCH /investigations/{id}/context` | Save typed intake answers and return updated state. |
| 02 | `POST /investigations/{id}/evidence` | Accept JSON text or a multipart screenshot. Return an evidence ID and review state, plus redacted OCR text or a clear OCR fallback state for images. |
| 02 | `PATCH /investigations/{id}/evidence/{evidence_id}`, `DELETE /investigations/{id}/evidence/{evidence_id}` | Confirm corrected text or remove an owned item. Delete returns `204`. |
| 03 | `POST /investigations/{id}/analyze` | Return `202` with a run ID and state. A repeat request for the active input revision reuses that run. |
| 03 | `GET /investigations/{id}` | Include the current run ID, stage, state, safe error or fallback notices, and the latest valid result. Poll while queued or running. |
| 04 | `GET /incidents`, `PATCH /incidents/{id}/status` | List the session's cases and update their user-managed status. Use the investigation ID as the incident ID. |
| 04 | `POST /investigations/{id}/report`, `GET /investigations/{id}/report` | Generate or retrieve the current report. Request `?format=txt` on GET for a UTF-8 attachment. |
| 05 | `GET /demo/scenarios`, `POST /demo/scenarios/{id}/load`, `POST /demo/reset` | List and load synthetic scenario data. Reset removes session cases and restores its transaction seed data. |

Use a stable API error envelope with a machine-readable code and a display-safe message. Return `409` when a report is requested before a current result exists or when analysis is blocked by an unreviewed screenshot. Use `422` for invalid field values, `413` for oversized evidence, and `415` for unsupported screenshot formats.

### Implemented Phase 02 wire details

- `POST /investigations` takes `{transaction_id}` (UUID), returns the complete case, and uses `201` for creation or `200` for reopening. One case exists per owned transaction. These endpoints require an existing demo cookie and never create a session; initial transaction requests still create one.
- Case responses contain `id`, `transaction_id`, `input_revision`, `workflow_state=collecting_context`, timestamps, authoritative `transaction`, `context`, `evidence`, and `analysis=null` before an analysis run exists; Phase 03 supplies the run and current result.
- Context PATCH accepts partial fields and `expected_revision`. `expected_payment`, `knows_sender`, `repayment_requested`, and `already_sent_money` use `yes|no|unknown`. `contact_channels` uses `call|whatsapp|sms|paytm_request|other`; `pressure_tactics` uses `urgency|threat|bank_avoidance|secrecy`. Both arrays use null for unanswered and [] for explicit none. Destination type is `unknown|same_sender|different_vpa|bank_account|payment_request|not_specified`; `requested_vpa` is optional, up to 256 characters. Unknown fields are rejected.
- Text evidence POST uses JSON `{type: message|call_summary, text, expected_revision}`. Screenshot POST uses multipart `file` and `expected_revision`; no framework disk spooling is used. Text is capped at 10,000 characters and a case at 20 evidence items. The entire multipart body is capped at 6 MiB, the image itself at 5 MiB, and decoded pixels at 16 million.
- Evidence responses contain `{evidence, input_revision}`. Evidence has ID, type, `review_state=confirmed|needs_review|ocr_failed`, redacted `ocr_text`/`confirmed_text`, safe metadata, notice, and timestamps. OCR fallback notices are `unreadable|ocr_unavailable`. Text is confirmed on submission as a user statement. Screenshots require explicit review.
- Evidence PATCH takes `{text, confirmed: true, expected_revision}`. DELETE takes `?expected_revision=N` and returns `204`. Creation, edit/confirmation, removal, and actual context changes advance the revision under a row lock. No-op saves preserve it; stale writes return `409 stale_revision`. OCR runs outside a database transaction and its revision is checked again before persistence.
- Phase 02 resource lookups return the same `404` for missing/invalid sessions, unknown IDs, foreign IDs, and evidence attached to another case. Phase 01 transaction endpoint behavior is preserved.

## Storage and evidence

- Use ordered PostgreSQL migrations and record applied versions. Store demo users and sessions, seeded transactions, investigations, typed user context, evidence, analysis runs, extracted signals, intel entities and relations, assessments, reports, and audit events. Each investigation links to one owner and one original transaction. Enforce that relationship in the database. Store INR amounts as integer paise and timestamps as timezone-aware values.
- Record actual transaction status as successful, pending, or failed. Treat unavailable facts as an explicit analysis outcome. Keep workflow state and user-managed case status in separate fields.
- Capture expected payment, sender familiarity, repayment request, contact channels, requested destination type and optional VPA, reported pressure, and whether the user already sent money. Preserve unknown answers. Treat pasted messages and typed call summaries as user statements, and confirmed OCR as user-reviewed text.
- Validate JPEG and PNG content, byte size, and decoded dimensions. Allow the image bytes to exist only during OCR processing. Persist evidence type, review state, sanitized metadata, and redacted text. Keep the preview in the browser, and revoke its object URL when it closes or the evidence is removed.
- Redact credential values before durable storage or provider requests. Send only the confirmed evidence text needed for extraction to Gemini, and mask unrelated personal identifiers there. Keep complete transaction references and any required comparison identifiers local. Logs and audit metadata contain IDs, event types, stage durations, and safe error codes. Keep evidence text and credential values out of them.
- Changes to context, confirmation, or evidence membership advance the case input revision. Invalidate the prior assessment and server-held report in the same transaction. Removing evidence also removes its persisted text, derived signals, and dependent result/report content. A previously downloaded file remains with the user.

## Analysis and reporting

The analyze endpoint persists a run as queued, and a bounded worker claims it atomically. Run states are queued, running, complete, and failed. Use a lease for running work so expired attempts can be recovered after interruption. Apply each persisted stage update and result only if the run still owns its lease and the case input revision is current. Keep failures resumable from saved input, and prevent an older run from restoring invalidated results.

The typed graph state carries the investigation ID, input revision, current stage, transaction facts, context, confirmed evidence, extraction and intelligence results, assessment, recommendations, and safe errors. Use one LangGraph graph with these four nodes.

1. **Transaction Context** reloads the owned mock transaction and verifies its actual status.
2. **Message Analysis** sends redacted evidence text to Gemini with structured output and validates it with Pydantic. Validate citations against the exact supplied text, discard unsupported extractions, and preserve unknowns. The prompt treats all evidence as data and exposes no tools. Retry once on timeout or invalid output.
3. **Risk Investigation** looks up exact identifiers in the seeded PostgreSQL intelligence records and computes destination matching locally. Apply versioned Python rules and preserve evidence IDs or rule IDs for every finding. Keep user claims, extracted evidence, simulated matches, and inferences distinguishable.
4. **Incident Resolution** builds explanations, safe guidance, and report data from the assessment and its sources. Include the PRD's verification and uncertainty language and use post-loss guidance when the user reports sending funds.

If extraction fails, show the provider limitation. Use validated transaction facts and structured user answers when they support a category. Otherwise use Unable to assess with actionable fallback guidance. A missing intelligence match means only that the available demo data returned no match.

Render a report from a persisted result for the current input revision. Keep transaction facts, user statements, evidence, findings, unknowns, recommendations, and generation timestamp visible in both the browser and text download. Store the report snapshot in PostgreSQL and generate the download from it.

## Implemented Phase 03 contracts

- `POST /api/v1/investigations/{id}/analyze` accepts `{expected_revision}` (strict nonnegative integer) and returns `202` with `run_id`, `input_revision`, `state`, `stage`, safe `error_code`, `notices`, and `result`. The request uses lookup-only ownership. Missing/foreign resources return the same `404`; stale revisions return `409 stale_revision`; unconfirmed screenshots return `409 evidence_review_required`.
- One run exists per investigation/revision. Queued, running, and complete runs are reused. An explicit POST requeues a failed current run with the same ID and a fresh attempt budget, removing its prior derived outputs. The case GET embeds this status in `analysis`; only complete current results are returned.
- Workflow states are `collecting_context`, `analysis_queued`, `analyzing`, `results_ready`, and `analysis_failed`. Run states remain `queued|running|complete|failed`; stages are `queued`, the four node names, and `complete`. Case status management remains Phase 04.
- Two lifespan-owned worker slots claim database work under case-then-run locks with `SKIP LOCKED`. A 60-second lease is renewed every 10 seconds; idle slots poll every second. Recovery reuses completed stage outputs. Three interrupted claims fail safely until explicit retry. Stage durations contain only numeric timings; raw provider errors and responses are never persisted or logged.
- Every worker write checks owner, current revision, unexpired lease, and fencing token. Actual context/evidence changes clear all run outputs, delete extracted signals and assessments, revoke leases, and restore intake state in the same transaction. Old run metadata remains without evidence text. No-op saves preserve a result. Phase 04 extends this same invalidation transaction to delete all report snapshots for the case.
- The graph reloads owned authoritative facts and confirmed evidence, extracts validated claims, performs exact local intelligence/destination checks and versioned Python classification, then creates deterministic guidance. Only a locally supported requested destination is compared; an identifier merely mentioned is not treated as that destination. Conflicting user/extracted repayment claims are shown as limitations.
- Extraction uses opaque evidence references and identifier placeholders. Citations must occur in exactly the supplied text; amounts and entity values are checked against their citations. Negated requests cannot be promoted by quoting a positive substring. Credential intent can be preserved as a safe enum before values are redacted, without retaining credentials; bare labels and safety advice are not sufficient. These checks are conservative English prototype rules.
- `BYTEBOT_EXTRACTION_MODE=gemini` uses server-only configured key/model, eight-second attempts and one retry for timeout or invalid output, with SDK retries disabled. Missing/unavailable extraction uses only supported saved/local input and marks the limitation. `fixture` explicitly accepts exact predefined synthetic inputs and labels every result; it rejects unknown fixture text.
- Assessments include category, summary, rule version, triggered rules, findings (`kind`, display text, source, reference, optional sanitized quote, rule ID), limitations, recommendations, generation time, extraction status/provider mode, and simulated exact-match details. Pressure types deduplicate as urgency, threat, and isolation (bank avoidance/secrecy). Same-ID matching carries zero risk reduction; transaction incompleteness takes category precedence while supported warnings remain.
- Frontend uses loopback 5174 (strict), API 8000, preview 4174 (strict), PostgreSQL 55433. Ports 5000, 5173, and 3306 are reserved for another project and must remain untouched; the original temporary PostgreSQL container remains on 55432. Browser suites accept `BYTEBOT_WEB_URL` and default to 5174.


## Implemented Phase 04 contracts

- Case responses add `case_status` (default `Open`) and `status_revision` (default 0). These are separate from `workflow_state` and `input_revision`. All six PRD statuses are user-entered, with unrestricted transitions. Status saves never advance input revision or invalidate analysis/reports.
- `GET /api/v1/incidents` returns `{incidents: [...]}` with ID, creation timestamp, authoritative transaction, case status/revision, and current completed category or null. It includes all owned cases, newest creation first, with ID as a deterministic tie-breaker. An initialized session with no cases gets an empty list; absent sessions get lookup-only 404 without a new cookie.
- `PATCH /api/v1/incidents/{id}/status` accepts `{status, expected_status_revision}` (strict nonnegative integer, extra fields forbidden), locks the owned case, and returns the updated incident summary. Stale status revisions return `409 stale_status`; invalid fields return 422. A no-op returns the saved summary without incrementing or auditing. Failed/stale writes do not overwrite another tab's status. The browser reloads only the saved status for conflict recovery, preserving intake drafts.
- `POST /api/v1/investigations/{id}/report` accepts `{expected_revision}` using the existing strict revision contract. Under the case lock, it requires a complete current run/assessment and creates one snapshot per case/input revision. It returns 201 on creation or 200 with the same ID/timestamp/content on reuse, including concurrent requests. A stale revision returns `409 stale_revision`; absent/incomplete current results return `409 analysis_required`.
- `GET /api/v1/investigations/{id}/report` returns the stored JSON snapshot, never generates implicitly, and checks current analysis before retrieval. A current result without a report returns 404. `?format=txt` generates `text/plain; charset=utf-8` with an ASCII report-ID attachment filename and `nosniff`. Unsupported formats return 422. Report and incident resources use the existing owner-derived cookie checks and identical foreign/missing 404 envelopes; every response remains `no-store`.
- Snapshot schema version 1 includes report/case/run identity, input revision, timestamp, status at generation, typed original transaction plus actual-status explanation, typed user answers, confirmed redacted evidence and source labels, validated extracted signals, the full validated assessment, explicit unanswered-context unknowns, and extraction notices. Amount signal values are formatted in INR from integer paise. No screenshot bytes, filenames, original OCR drafts, upload metadata, raw provider outputs, or credentials are added. Generation makes no model call.
- React renders `/investigations/:id/report` from that snapshot with escaped text and downloads the server-generated UTF-8 attachment. Download verifies report identity against the reviewed snapshot; navigation/window focus reloads and clears old content before revalidation. An invalidation response removes the report and offers saved-input review/reanalysis. Status changes leave `status_at_generation` unchanged. A user's already downloaded file cannot be revoked.
- Migration 004 adds `incident_reports`, `audit_events`, and status fields. `investigation_store.bump` physically deletes report snapshots in the same case-locked transaction that erases assessments, signals, and run outputs. Report generation uses the same lock, preventing stale report publication after an edit. Existing lease fences remain unchanged.
- Audit actions are `investigation_created`, `context_updated`, `evidence_submitted`, `evidence_updated`, `evidence_removed`, `analysis_completed`, `report_generated`, and `status_updated`. They commit with the corresponding action; no-op writes/reused reports create no duplicate events. Actor is `user` or `system`; metadata is limited by per-action schemas to resource UUIDs, input/status revisions, evidence type, and old/new status enums. Historical backfill uses original investigation/evidence creation and completed-run update timestamps, marks `backfilled=true`, and invents no absent history. Audit rows retain no evidence content after deletion and cascade with their case during reset.

## Implemented Phase 05 contracts

- `GET /api/v1/demo/scenarios` is a public synthetic catalog, with `{extraction_mode, scenarios: [{id,title,description,evidence_text}]}`. It creates no session, exposes no owned IDs, and uses the actual configured extractor mode.
- `POST /api/v1/demo/scenarios/{id}/load` requires an existing session and accepts `{evidence_mode: "text"|"manual"}`, default text; extra fields are rejected. It returns `{scenario_id,transaction_id,investigation,created}` with 201 for a new case and 200 for reopening. Unknown scenario IDs and absent sessions return lookup-only 404. One transaction atomically copies a missing owned scenario transaction, creates the case, and uses the normal validated answers/redacted evidence/revision/audit helpers. Manual mode omits evidence; D always has none. Existing cases are returned untouched, regardless of mode. No analysis or report is started.
- Seeds add five `scenario-a` through `scenario-e` templates without changing the original three or existing owners. New sessions have eight transactions. Existing owners gain only the requested missing scenario transaction on load, or all eight on reset. Each scenario is an independent successful ₹5,000 credit with the original same sender VPA needed by fixtures. No migration or dependency change is required.
- `POST /api/v1/demo/reset` accepts no body or an empty object and rejects owner/resource selectors. Existing sessions only; invalid/missing sessions return 404 without a cookie. It preserves owner/cookie and returns `{status:"reset",transaction_count:8}` after commit. Required templates are checked before deletion. Reset locks owner then owned cases in ID order, deletes owned investigations and dependent context/evidence/runs/signals/assessments/reports/audit, deletes owned transactions, and copies eight templates with fresh IDs. Every operation rolls back together on failure. Shared intelligence/templates and other owners are untouched.
- All case creation and scenario loading acquire the owner lock before case locks, serializing with reset. Existing case writers and workers keep case-before-run ordering. Reset never holds a lock during provider/OCR work. Missing cases now count as lost worker leases; late writes cannot restore reset state. A delayed OCR upload rechecks ownership/revision before persistence and receives 404 after reset. Repeated reset restores equivalent seed content, with new resource IDs each time.
- History supplies selector, manual-evidence option, mode/provenance labels, status/error announcements, retries, and confirmed reset. Reset is reached through normal navigation so the intake's unsaved-change guard still applies. Report downloads/focus checks reject reset snapshots. Mobile header height accommodates wrapped navigation and badge.
- Explicit fixture mode checks raw confirmed text against canonical synthetic messages before identifier masking. Any edited/unknown message takes the existing extraction-unavailable/local fallback. Gemini mode never silently substitutes fixtures. Screenshot OCR must still be reviewed and corrected; exact confirmed text can use the fixture adapter, with screenshot provenance preserved.
